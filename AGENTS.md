# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

ZMK firmware **config** (not the ZMK source) for the Kinesis Advantage 360 Pro — a wireless split keyboard with two independent nRF52840 halves (`adv360_left`, `adv360_right`). Editing here means editing device-tree keymaps and Kconfig, then producing two `.uf2` firmware files, one per half.

There is no application source to compile in this repo. The ZMK application, Zephyr, and the board's build machinery come from a **custom ZMK fork** pulled by west, pinned in `config/west.yml`: `refil/zmk@adv360-z3.5-2` (not upstream `zmkfirmware/zmk`). Upstream ZMK docs mostly apply, but RGB Underglow / Backlight / Power Management behave differently on this fork (see `README.md` "note").

## Building firmware

Two paths, both produce `left.uf2` + `right.uf2`:

- **GitHub Actions** (`.github/workflows/build.yml`) — push any commit; download the artifact. Builds two variants: `firmware-no-clique` and `firmware-clique` (the latter enables ZMK Studio).
- **Local container** (`Makefile`, needs Docker or Podman — Podman preferred if both present, plus `make`):
  - `make` — build both halves → `firmware/*.uf2`
  - `make left` — build left half only
  - `make clean_firmware` — delete `firmware/*.uf2` (keeps the build image)
  - `make clean_image` — remove the Docker image only
  - `make clean` — both of the above

Under the hood the container runs `bin/build.sh`, which calls `west build -s zmk/app -b adv360_left|adv360_right -- -DZMK_CONFIG=/app/config`. To build a single board directly inside a ZMK-toolchain environment (e.g. debugging one half):

```
west build -s zmk/app -p -d build/left  -b adv360_left  -S studio-rpc-usb-uart -- -DZMK_CONFIG="$PWD/config" -DCONFIG_ZMK_STUDIO=y
west build -s zmk/app -p -d build/right -b adv360_right -- -DZMK_CONFIG="$PWD/config"
```

Note the asymmetry: the **left** half is the one built with ZMK Studio (`studio-rpc-usb-uart` snippet + `CONFIG_ZMK_STUDIO=y`); the right half is not. This is the "Clique" build.

## Editing the keymap

`config/adv360.keymap` is the **single source of truth** — the device-tree keymap actually compiled into firmware. `adv360_left.keymap` and `adv360_right.keymap` are thin wrappers that only `#include "adv360.keymap"`, so both halves share one keymap. Keep at least one space between behaviours; a malformed grid breaks the build.

The GUI [Nick Coutsos keymap editor](https://nickcoutsos.github.io/keymap-editor/) reads and writes **`adv360.keymap` directly**, using `config/info.json` for the physical layout (the `LAYOUT` object: 76 keys with `row`/`col`/`x`/`y`/`w`). So editor edits are committed straight to the `.keymap` (see commits authored by `keymap-editor[bot]`, e.g. `da9af49`, which touch `adv360.keymap` + `info.json`).

There is **no `keymap.json`** — it was a stale artefact from an older editor flow, not read by the build (grep the repo: nothing references it) and never written by the current editor, so it was removed. Do not reintroduce a parallel JSON keymap; edit `adv360.keymap` (by hand or via the editor). `UPGRADE.md` still references `keymap.json` for the V2→V3 migration, but that guidance predates its removal.

Combos and other position-dependent features need exact matrix key positions — see `assets/key-positions.md` (image + text).

### Keymap structure

Layers in `config/adv360.keymap` (index → `display-name`): `0 Base`, `1 Kp` (keypad), `2 Fn`, `3 Mod`, `4 Red`, `5 Purple`. Layers `6 Cyan` and `7 Yellow` remain `status = "reserved"` (placeholders holding an index/colour slot, not populated). The layer's colour comes from its **index**, per the table in `README.md` (index 4 = red, 5 = magenta/purple), not from its `display-name`. Layer switching uses `&mo`/`&tog` referencing these indices, so **renumbering or reordering layers breaks the `&mo N` / `&tog N` references** scattered through every layer. Red/Purple are currently all-`&trans` and have no access key — unreachable until an `&mo 4`/`&tog 4` (etc.) is bound somewhere.

Custom behaviours defined inline: `hm` (homerow mods, hold-tap) and `macro_ver` (the version macro, see below). `config/macros.dtsi` holds additional macros, `#include`d into the `behaviors` block.

## `config/version.dtsi` is generated — do not edit

`version.dtsi` is auto-generated by `bin/get_version_local.sh` (local, invoked by `make`) and `bin/get_version.sh` (CI). It encodes build date + branch prefix + commit hash into the `macro_ver` macro, typeable on the keyboard via **Mod+V**. The Makefile runs the generator before building and `git checkout config/version.dtsi` after, so the working tree stays clean. The committed file is empty by design; leave it alone.

## Board / Kconfig configuration

Board definition: `config/boards/arm/adv360/` (`.dts` per half, `*_defconfig`, `Kconfig*`, pinctrl, dtsi). Most feature flags live in **`adv360_left_defconfig`** — it is the primary knob file. Commonly-toggled options (documented in `README.md`):

- `CONFIG_ZMK_HID_KEYBOARD_EXTENDED_REPORT` — set `=y` for F13–F24 / INTL keys under NKRO.
- `CONFIG_BT_BAS` — set `=y` to report battery over BLE (off by default; can wake some hosts).
- `CONFIG_ZMK_RGB_UNDERGLOW_MOD_COLOR` — hex RGB for the Caps/Num/Scroll-lock indicator LEDs.

When a setting affects both modules (e.g. indicator colour), change **both** `adv360_left_defconfig` and `adv360_right_defconfig`.

## Conventions

- Firmware output (`firmware/*.uf2`) is gitignored.
- The default/main branch here is `V3.0`. `UPGRADE.md` covers the V2→V3 keymap-matrix migration (the source of most user merge conflicts).
- Flashing: put each half into bootloader (Mod+macro1 left, Mod+macro3 right, or physical reset button) and copy the matching `.uf2`; `settings-reset.uf2` at repo root clears stored settings. Full procedure in `README.md`.
